# rhbot — Robinhood Chain ミームコイン スパイク検知ボット

Robinhood Chain（Ethereum L2 / Arbitrum Orbit、DexScreener 上の chainId は `robinhood`）のミームコインを
DexScreener API で監視し、次の 2 種類のイベントを **Telegram** に通知します。

| 種類 | 条件（デフォルト値） | 通知の見出し |
| --- | --- | --- |
| 🚀 **新規ローンチ** | 作成から **12h 以内**・**時価総額 $1M 以上**で、1h 出来高が $25K / $100K / $500K の各段階を超えた | `🚀 新規ローンチ ｜ 規模 小/中/大` |
| ♻️🔥 **再点火**（最重視） | 全盛期に**時価総額 $800K 以上**を記録し、そこから冷え、**成立したレンジ**を **+6% 以上**上抜け | `♻️🔥 再点火 ｜ 出来高 低/中/高` |
| 🔥 **静穏から復活** | **6h 以上**経過し、1h 出来高が平常の **3 倍以上** かつ価格 **+30% 以上** | `🔥 静穏から復活 ｜ 出来高 低/中/高` |
| 🔥 **レンジ上抜け** | **6h 以上**経過し、ヨコヨコのレンジ上限を **+12% 以上**上抜けた | `🔥 レンジ上抜け ｜ 出来高 低/中/高` |
| 🔥 **急変** | 5 分足で **+20% 以上** 動いた | `🔥 急変 ｜ 出来高 低/中/高` |

### 再点火をなぜ最優先で拾えるのか

いちばん価値があるのは「初動で時価総額 $5M をつけ、下がって $1.0〜1.5M でレンジを組み、そこを抜ける」型です。
**過去に大きな時価総額をつけたこと自体が、market がその評価を実際に認めた証拠**になります。
無名の銘柄が偶然動いたのとは違うため、レンジ抜けのしきい値を +12% → **+6%** まで下げても誤検知が増えません。
つまり**より早く通知できます**。

### 特定の例に合わせ込んでいないこと

判定はすべて**倍率と時間**で書かれており、`$5M` のような具体的な金額はロジックに埋め込まれていません。
ATH は全銘柄について自動記録されるので、$2M でも $10M でも $50M でも同じ基準がそのまま効きます。
例を 1 つずつ積み増す必要はありません。

**レンジは「窓内の最高値」ではなく、成立を確かめてから使います。** 最高値をそのまま天井とすると、
下落し続けている最中の一点を天井と誤認し、ただの戻りで通知してしまいます。そこで次の 3 つを満たしたときだけ
レンジと認めます。

| 条件 | 既定 | 意味 |
| --- | --- | --- |
| 帯の幅（上限÷下限-1） | 150% 以下 | 一定の幅に収まっている＝トレンド中ではない |
| 観測期間 | 12 時間以上 | 一時的な小休止ではない |
| 観測点数 | 20 点以上 | 判断に足るだけ見えている |

**窓は固定せず、長い方から順に縮めて試し、最初に成立したものを採ります。** 固定すると、その中に初動スパイクが
1 本入っただけで幅の条件に落ち、その後どれだけきれいにレンジを組んでいても認識できません。段階的に縮めれば
スパイクを含む窓は落ち、落ち着いた区間だけが残ります。

実例（$LOOM）: 初動で MC $1.15M → 崩れて $280K〜$620K で 12 時間ヨコヨコ → 上抜け。
20 時間の窓はスパイクを含むため不成立、12 時間の窓でレンジ（幅 121%）が成立し、$670K の時点で検知します。
実際の高値は $1.67M なので、その 4 割の水準で鳴ることになります。

判定も表示も**時価総額で統一**しています。ミームコインの価値をそのまま表す単位であり、
供給量が変わっても比較が崩れないためです。そのために各銘柄の全盛期（最高時価総額・最大 1h 出来高・最高値と、
それぞれの時刻）を `pairs` テーブルに、時価総額の推移を `snapshots` に永続保存しています。
スナップショットの保持期間を過ぎても消えないので、何日前の全盛期でも判定に使えます。
さらに全盛期の時価総額が大きい銘柄は、いま静かでも `PRIORITY_POLL_INTERVAL_SEC`（既定 45 秒）ごとに見張ります。
再点火はこうした銘柄から起きるため、dormant の 4 分間隔では遅すぎるからです。

同じ値動きでの比較:

```
全盛期 MC $5M → $1.0〜1.5M でヨコヨコ → 上抜け
  MC $1.53M (レンジ + 2.0%)   全盛期あり: —          履歴なし: —
  MC $1.59M (レンジ + 6.0%)   全盛期あり: 🔔 再点火   履歴なし: —
  MC $1.68M (レンジ +12.0%)   全盛期あり: 🔔 再点火   履歴なし: 🔔 検知
```

届く通知:

```
♻️🔥 再点火 ｜ 出来高 中 🟧
$PHNX  Phoenix

全盛期 MC $5.00M（2日2時間前） → いま $1.60M（32%）
レンジ $1.00M〜$1.50M を +6.7% 上抜け
　（幅 50% で 38時間0分 形成）
底値から +60.0%
```

「ヨコヨコから急騰」には性質の違う 2 つの型があります。取引が止まっていた銘柄が動き出す**静穏型**と、
出来高は元から多いが価格が一定幅を往復していてそこを抜ける**レンジ抜け型**です。
出来高の突発率だけを見ると後者を取りこぼします（24h で $8.78M を捌いていた銘柄は、価格が 90% 飛んでも
「平常より静か」と評価されるため）。レンジ抜けは +90% になるのを待たず、レンジを超えた時点で判定できます。

どちらも流動性 $5K 未満、買い件数が少なすぎるペア（単発の wick）は除外します。しきい値はすべて `.env` で変更できます。

## 仕組み

```
┌──────────────────────── 監視対象の発見 ────────────────────────┐
│ ① DexScreener /latest/dex/search   (クエリ × 最大30件, chainId で絞る) │
│ ② DexScreener /token-pairs/v1      (WETH 等の quote トークンの全プール)   │
│ ③ DexScreener token-profiles/boosts (宣伝・ブースト中トークン)            │
│ ④ チェーン RPC eth_getLogs          (Uniswap V2/V3/V4 のプール作成イベント)│
└───────────────────────────────┬────────────────────────────────┘
                                ▼
                 SQLite (pairs / snapshots / alerts)
                                │
        ┌───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
   hot (45s 更新)        dormant (4min 更新)        dead (30min 更新)
   直近に出来高あり/新規    低迷中 ← 復活検知の主戦場    流動性ほぼゼロ
        └───────────────────────┼────────────────────────┘
                                ▼
              detectors: newLaunch / revival → Telegram
```

- **RPC 監視 (④)** は DexScreener の search が 30 件までしか返さない弱点を補うためのものです。
  ファクトリのイベントを直接読むので、どの DEX（Uniswap 系フォーク含む）でも新規プールを作成直後に検知できます。
  見つけたプールは DexScreener にインデックスされ次第、監視対象に入ります。
- **dormant ペアも定期的に更新し続ける** ことが復活検知の要です。流動性が残っている限り監視から外しません。
- 同じトークンに複数ペア（WETH / USDC 等）があっても通知はトークン単位で 1 回です。

## セットアップ

必要なもの: **Node.js 22.13 以上**（`node:sqlite` を使うため。外部の DB 不要）

```bash
git clone https://github.com/cony-horizon/rhbot.git
cd rhbot
npm install
cp .env.example .env
```

### 1. Telegram ボットを作る

1. Telegram で [@BotFather](https://t.me/BotFather) に `/newbot` → トークンを取得 → `.env` の `TELEGRAM_BOT_TOKEN` に設定
2. 作ったボットに何か話しかける（グループで使うならグループに追加して話しかける）
3. ブラウザで `https://api.telegram.org/bot<トークン>/getUpdates` を開き、`"chat":{"id":123456789` の数字を `TELEGRAM_CHAT_ID` に設定
   （グループは負の数になります。複数はカンマ区切り）

### 2. 疎通確認

```bash
npm run probe -- telegram   # テストメッセージが届けば OK
npm run probe               # DexScreener 検索・トークンプール・RPC の疎通と取得件数を表示
```

> `tsx: command not found` が出た場合は、同じコマンドをもう一度実行してください。
> 各 npm script の先頭に `scripts/preflight.mjs` が入っており、依存パッケージの欠落を検出して
> `npm install --include=dev` で自動復旧します。

### 3. 更新

GitHub 側を更新しても手元のファイルは自動では変わらない。取得からビルドまでは次の 1 コマンド。
`.env` と `data/` には触れないので、設定と蓄積した履歴は残る。

```bash
npm run update   # git pull → npm install → build
npm start
```

ZIP で取得したフォルダには git の情報が無いため、この方法は使えない。
その場合は `npm run update` が clone し直す手順を案内する。

### 4. 起動

```bash
npm run dev      # 開発（ファイル変更で自動再起動）
# または
npm run build && npm start
```

Docker の場合:

```bash
docker compose up -d --build
docker compose logs -f
```

VPS で常駐させるなら `pm2 start npm --name rhbot -- start` か上記 Docker を推奨します。

## Telegram コマンド

| コマンド | 説明 |
| --- | --- |
| `/status` | 監視ペア数（hot/dormant/dead）、直近 24h のアラート数、RPC ブロック、API 使用量 |
| `/top [n]` | 1h 出来高上位ペア |
| `/alerts [n]` | 直近のアラート履歴 |
| `/test` | 通知の見本を送る。監視中ペアの実データを使うので、配信経路と表示の両方を確認できる |
| `/watch <アドレス>` | ペア or トークンアドレスを手動で監視追加（自動削除されません） |

| `/list` | 手動監視中の一覧 |

| `/filtered [n]` | スキャム判定で止めた通知と、その理由 |
| `/why <アドレス>` | 指定銘柄のリスクを今の数値で採点し、内訳を表示 |
| `/report` | 日次レポート（成績・良かった/悪かったコール・止めたが伸びた銘柄・改善案）を今すぐ出す |
| `/outcomes [n]` | 直近の通知の 15m / 1h / 4h 後の変化と最大上昇 |
| `/smart [n]` | 勝った復活銘柄の急騰前に買っていたウォレット台帳（複数銘柄で ⭐） |
| `/wallet <アドレス>` | ウォレットの買い履歴 |
| `/mute [分]` / `/unmute` | 通知を一時停止 / 再開（検知は継続し `/alerts` に残ります） |
| `/config` | 現在の検知しきい値 |

`TELEGRAM_CHAT_ID` に含まれない chat からのコマンドは無視されます。

### スキャム除外フィルタ

バンドルや洗浄取引で出来高を作った銘柄を、DexScreener API で取れる値だけで判定して通知から除外します。
画面にある平均売買金額やトレーダー数は API に無いため、**出来高がプールの深さに対して過大か**を軸にしています。
出来高は人為的に膨らませられますが、流動性と時価総額は同じようには膨らませられないためです。

| 指標 | 加点 | 意味 |
| --- | --- | --- |
| 1h 出来高 ÷ 流動性 | +18 / +35 | 4x / 8x 以上。実需で 1 時間にプールの数倍が回ることは稀 |
| 1h 出来高 ÷ 時価総額 | +10 / +20 | 40% / 80% 以上 |
| 流動性 ÷ 時価総額 | +12 / +25 | 5% / 2% 未満。値札だけ高く売り抜けられない |
| 薄いプールでの急騰 | +25 | 流動性 $150K 未満で +1000% 以上。少額で値を動かせる証拠 |
| 流動性の絶対値 | +20 | $20K 未満 |
| 平均取引額 | +12 | $40 未満かつ 100 件超。件数稼ぎの塵取引 |
| ローンチ直後の出来高 | +15 | 60 分以内に流動性の 3 倍超。同一ブロックで買いを固めるバンドルの典型 |

合計が `SCAM_SCORE_THRESHOLD`（既定 50）以上なら通知しません。止めたものは履歴に理由付きで残り、
`/filtered` で確認できます。**本来ほしかった銘柄が混ざっていたらしきい値を上げてください。**

実測例（利用者が報告した Robinhood Chain の $PUMPS）:

```
$PUMPS  リスク 95/100  → 通知しない
  +35  1h 出来高が流動性の 9.1 倍（洗浄取引の疑い）
  +20  1h で時価総額の 93% が取引された
  +25  流動性 $88,000 で +33753% の急騰（少額で値を動かせる）
  +15  ローンチ 41 分で流動性の 9.1 倍の出来高（バンドルの疑い）

健全な復活銘柄  リスク 12/100  → 通知する
  +12  流動性が時価総額の 4.9% と薄い
```

#### 参加者の厚み — 出来高比だけでは本物を弾いてしまう

上の表は「出来高がプールに対して過大か」を軸にしていますが、これだけでは**本物の初動ランナーほど強く弾かれます**。
本当に人が集まっている銘柄は、当然プールを何倍も回すからです。

利用者が報告した反例（どちらも Robinhood Chain、ローンチ直後）:

| | $SNOWBALL（本物） | $PUMPS（バンドル） |
| --- | --- | --- |
| 1h 出来高 ÷ 流動性 | **18.1x** | 9.1x |
| 1h 取引件数 | **11,811** | 1,204 |
| 平均取引額 | **$144** | $663 |
| 買いの比率 | **51%** | 73% |

倍率では本物のほうが「悪い」。分かれるのは下の 3 行、つまり**小口が大量に、売り買い拮抗で流れているか**です。
これは多数の独立した参加者がいる証拠で、少数のウォレットが大きな玉を一方向に回すのとは形が違います。

| 条件 | 既定 | 扱い |
| --- | --- | --- |
| 1h 取引件数 | 2,000 件以上 | **必須** |
| 平均取引額 | $40〜$500 | **必須** |
| 買いの比率 | 40〜60% | 加点（初動は買い偏重になりやすいので必須にしない） |

満たした銘柄では**出来高比による減点**（1h出来高÷流動性・1h出来高÷時価総額・ローンチ直後の出来高）を行いません。
薄いプールでの急騰など、厚みと無関係な減点はそのまま残ります。

件数と拮抗だけを装って大口を往復させる洗浄取引に抜け道を与えないため、上 2 つは必須にしてあります。

```
$SNOWBALL  リスク 25/100  → 通知する
  +25  流動性 $94,000 で +1900% の急騰（少額で値を動かせる）
  👥 参加者の厚みあり — 取引 11,811 件 / 平均 $144 の小口中心 / 売り買い拮抗（買い 51%）
```

調整は `.env` の `SCAM_BREADTH_*`。`/why <アドレス>` で任意の銘柄の厚みと採点を確認できます。

### `/ranges` — いま何を待っているか

再点火の通知は「レンジを上抜けた瞬間」に鳴ります。その一瞬まで何も出ないと、
ボットが何を見張っているのか分からないままになるので、待機中の一覧を出せるようにしました。

```
🟡 $PHNX — あと +6.7%で再点火
　帯 $1.00M〜$1.50M（幅 50% / 29時間15分）
　いま $1.49M（帯の 98% 地点・全盛期の 30%）| 全盛期 $5.00M
```

- **あと +X%** … その時価総額に届いた時点で通知が出ます（帯の上限 +`REIGNITE_BREAKOUT_PCT`）
- **帯の X% 地点** … 上限に張り付いているのか、底で沈んでいるのか
- **全盛期の X%** … `REIGNITE_COOLED_RATIO` 以下まで冷えていれば再点火の下地あり
- 🔔 条件到達 / 🟠 あと 5% / 🟡 あと 15% / ⚪ それ以上

条件を満たしていない銘柄は `⏸ 再点火の条件未達` と表示します（帯は組んでいるが全盛期が小さい、
まだ十分に冷えていない、など）。

一覧の計算は検知器と同じコードを共有しているため、「一覧には出るのに鳴らない」は起きません。
テストでも、一覧が示した上抜け価格まで実際に上げると通知が出ることを確認しています。

起動直後は履歴が足りず何も出ません。帯として認めるには `RANGE_MIN_HOURS` 以上・
`RANGE_MIN_SAMPLES` 点以上の観測が要ります。

### 反省の仕組み（結果追跡と日次レポート）

コールの質を上げるには「何が当たって何が外れたか」を毎日、感覚ではなく数字で振り返る必要があります。
ボットは通知（止めたものも含む）の**その後**をスナップショットから自動で埋めます。追加の API 呼び出しはありません。

- 15 分 / 1 時間 / 4 時間 / 24 時間後の変化率、24 時間内の最大上昇と最大下落
- **的中** = `OUTCOME_HIT_WINDOW_HOURS`（4h）以内に `OUTCOME_HIT_PCT`（+30%）以上
- **失敗** = 猶予内に `OUTCOME_BUST_PCT`（-50%）以下

毎朝 `REPORT_HOUR_JST` に前日分（結果が確定した通知のみ）を集計して送ります。

```
📊 日次レポート 9/7
種別別の成績
♻️ 再点火     3件  的中  67%  平均最大 +48%  平均DD -12%
🚀 新規       4件  的中  25%  平均最大 +21%  平均DD -38%
合計 的中率 43%（3/7）　前日比: 20% → 43%

🏆 良かったコール   ・$R1 ♻️ 再点火 ｜ 最大 +50%（60分後）｜ 4h +50%
💀 悪かったコール   ・$N2 🚀 新規 ｜ 最大 +0% ｜ 4h -60% ｜ 最大DD -60%
🚫 止めたが伸びた銘柄（1/2 件）・$GEM ｜ 最大 +100% ｜ リスク 55
→ SCAM_SCORE_THRESHOLD を 60 前後まで上げると拾えた可能性

📈 傾向と改善案
・売買「買い偏重」の的中 0%（3件） vs それ以外 75% → 低い。絞る方向で見直す候補: NEW_MIN_BUYS_H1
```

「傾向と改善案」は属性（種別・出来高水準・リスク帯・売買の偏り・時間帯・経過時間）ごとの的中率を比べ、
`REPORT_MIN_SAMPLES` 件以上あって 20 ポイント以上差があるものを、対応する設定名と一緒に挙げます。
**設定を自動で書き換えることはしません。** 提案を見て `.env` を変えるのは利用者です。

### スマートウォレット台帳

復活系の通知が**的中**と確定すると、その急騰の前 `SMART_HARVEST_WINDOW_HOURS`（6 時間）に
そのプールで買っていたウォレットを RPC の Swap イベントから集めます（DexScreener には無いデータです）。

- トレーダーは **tx.from** で特定します。イベント中の sender/recipient はルーターや PoolManager を
  指すことが多く（特に Uniswap v4）、人を表さないため
- Uniswap v2 / v3 / v4 の Swap に対応。v4 は PoolId をトピックで絞ります
- 買いの向きは token0/token1 の並び（アドレス昇順、ネイティブ ETH は 0x0 で先頭）から判定
- 窓内の Swap が `SMART_MAX_SWAPS` を超える銘柄は収穫しません（作られた出来高の疑い）

同じウォレットが**複数の勝ち銘柄**に早期から入っていれば ⭐（`SMART_MIN_HITS`）。`/smart` で一覧、
`/wallet <アドレス>` で履歴。将来はこの台帳のウォレットの動きをシグナルの参考にする土台です。
RPC の負荷を抑えるため、収穫は 10 分ごとに 2 銘柄までです。

### 自己診断

「通知が来ない」が正常（市場が静か）なのか異常（設定ミス・API 変更）なのかは利用者から見分けが
つかないため、対象チェーンのペアを 5 回連続で 1 件も取得できなかった場合、ボット自身が Telegram に
警告を送ります（同じ警告は 6 時間に 1 回まで）。

`npm run probe` は、`CHAIN_ID` に一致するペアが 0 件だったとき、実際に返ってきた chainId の一覧を
出力します。DexScreener 側でチェーン名が変わっても、そこから正しい値が分かります。

## チューニングガイド

`.env` を編集して再起動すると反映されます。主なノブ:

### 復活スパイク（🔥）

| 変数 | 既定 | 上げると | 下げると |
| --- | --- | --- | --- |
| `REVIVAL_PRICE_CHANGE_PCT` | 30 | 通知が減る、確度が上がる | 早く気づけるがノイズ増 |
| `REVIVAL_VOL_SPIKE_RATIO` | 3 | 「本当に突発」なものだけ | じわ上げも拾う |
| `REVIVAL_MIN_VOL_H1_USD` | 10000 | 小型を除外 | 小型も拾う |
| `REVIVAL_LOOKBACK_MIN` | 120 | ゆっくりした上昇も拾う | 直近の急騰のみ |
| `REVIVAL_MIN_AGE_HOURS` | 20 | 新規ローンチとの境界 | — |
| `REVIVAL_COOLDOWN_MIN` | 180 | 同一銘柄の連投を抑える | — |
| `REVIVAL_ESCALATION_PCT` | 50 | クールダウン中でも更に +50% で再通知（0 で無効） | — |

「30〜40% 以上」を確実に拾いたいなら `REVIVAL_PRICE_CHANGE_PCT=30` のまま、ノイズが多ければ 40 に。
ローンチ直後の乱高下を復活扱いしたくない場合は `REVIVAL_MIN_AGE_HOURS` を 24〜36 に上げてください。

### 新規ローンチ（🚀）

| 変数 | 既定 | 説明 |
| --- | --- | --- |
| `NEW_VOL_H1_TIERS_USD` | 25000,100000,500000 | 各段階を超えるたびに 1 回通知。1 段階だけにしたければ `50000` のように 1 つだけ書く |
| `NEW_MAX_AGE_HOURS` | 20 | これ以降は復活検知側に引き継ぐ |
| `NEW_MIN_BUYS_H1` | 15 | 買い件数の下限（bot 1 件の大口だけ、を除外） |
| `NEW_MIN_MC_USD` | 1000000 | 時価総額の下限。重心は再点火にあるので、新規は規模のあるものだけに絞る |

### 共通

- `MIN_LIQUIDITY_USD` (5000): 流動性下限。ラグ・ハニーポットの多くはこれで落ちます
- `QUOTE_SYMBOLS`: `WETH` などに絞ると USDC ペア等を無視
- `DORMANT_POLL_INTERVAL_SEC` (240): 復活検知の反応速度。小さくすると API 消費が増えます

### API 使用量の目安

DexScreener 無料 API は **300 req/分**（search / pairs / tokens）と **60 req/分**（profiles / boosts）。
ペア更新は 30 件 / 1 リクエストなので、hot 300 ペア + dormant 3000 ペアでも
毎分 20 リクエスト程度に収まります。`/status` の「DexScreener リクエスト累計」で確認できます。

### RPC について

`RPC_URL` 既定の公式パブリック RPC（`https://rpc.mainnet.chain.robinhood.com`）は bot 向けに保証されていないため、
429 が出る場合は `RPC_BLOCK_CHUNK` を下げるか `RPC_SCAN_INTERVAL_SEC` を上げるか、
[GetBlock](https://docs.getblock.io/api-reference/robinhood) 等のプロバイダの URL に差し替えてください。
RPC を使いたくない場合は `RPC_URL=` と空にすると DexScreener のみで動作します（新規ローンチ検知の網羅性は落ちます）。

## 既知の制約

- DexScreener の `search` は全チェーン横断で最大 30 件しか返しません。`DISCOVERY_SEARCH_QUERIES` を増やす、
  `DISCOVERY_TOKEN_ADDRESSES` に主要 quote トークンを列挙する、RPC 監視を有効にする、の 3 つで補っています。
- pump.fun 型ローンチパッド（ボンディングカーブ）上のトークンは DEX にマイグレーションされるまで RPC 監視には現れません。
  DexScreener がそれらを掲載していれば search / profiles 経由で拾えます。
- DexScreener 側で価格 (`priceUsd`) や `pairCreatedAt` が欠けているペアは対象外になります。
- 本ツールは通知のみで売買は行いません。投資判断は自己責任でお願いします。
